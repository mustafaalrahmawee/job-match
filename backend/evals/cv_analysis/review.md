# Review of the samples: `cv_analysis`

Checked is each sample, not the model: is the case fair, is the gold solution (`gold.json`) right, and does the CV read as real? The samples are written by Claude Code (Fable 5.1) with the `sample-writer` subagent; glm-5.3 reviews them with `pnpm evals review cv_analysis` – never the writer and never a model under test (EV-24, EV-25). Workflow: skill `/eval-samples cv_analysis`.

## Rules

- job-match is a web app for people applying for jobs in Germany. In this unit (UC-04) the applicant uploads a CV as PDF; the model reads the document (text layer or scan, German or English) and returns one JSON object: `is_cv`, `language`, `suggested_role` from a fixed list, `positions`, `skills`, `education`, `highest_degree`, `languages`, and in German `strengths`, `weaknesses`, `tips`. Everything comes from the document only; for a non-CV `is_cv` is false and every list is empty.
- The role list: Frontend, Backend, Fullstack, Mobile, Data, DevOps, QA, UX/UI, IT-Support, IT-Projektmanagement, Andere.
- Each case has two folders with the same id `NN-<role>-<short-topic>`, e.g. `03-backend-ten-years-scan`:
  - `samples/<case>/gold.json` – the gold solution
  - `corpus/cvs/<case>/index.html` – the CV as plain HTML, written from `gold.json` backwards; `bash backend/evals/corpus/cvs/build.sh` renders it to `cv.pdf`. The HTML sets `@page { size: A4; margin: 15mm }` or similar and needs no external files. A scan case carries `<meta name="layout" content="scan">` in its head; it is rendered as a page image without a text layer and must fit on one A4 page.
- Fields of `gold.json`:
  - `id` – the folder name
  - `group` – `typical`, `edge` or `hard`
  - `focus` – one sentence: what the case tests
  - `language` – `de` or `en`: the language the CV is written in
  - `is_cv` – `false` for a document that is not a CV (invoice, cover letter, certificate); then every list is `[]`, `role` is `Andere`, `accepted_roles` is `["Andere"]` and `highest_degree` is `null`
  - `role` – the role a recruiter would assign from the latest stations and the skills used there
  - `accepted_roles` – every role a careful recruiter could defend, always including `role`; usually one or two, e.g. `["Frontend", "Fullstack"]`
  - `positions` – every work station in the document, `[{"employer": "...", "title": "...", "years": "2021–2024"}]`; `employer` is the name as printed, without "GmbH" or "AG" (the check accepts both); internships and working-student jobs count when the document lists them as stations
  - `must_skills` – skills the document names that the answer must contain, `[{"name": "Vue.js", "synonyms": ["Vue", "Vue 3"]}]`; a skill counts as found when any spelling appears as a whole word in one entry of `skills` (`Java` does not match `JavaScript`); name the spellings the document uses
  - `absent_skills` – skills the document does not mention anywhere, but which the model is tempted to add for this role, e.g. `["Kubernetes"]` for a DevOps CV that only names Docker; a hit in `skills` is a failure
  - `languages` – the spoken languages as printed, e.g. `["Deutsch", "Englisch"]`; count and names must match, the level may be worded differently
  - `highest_degree` – a distinctive part of the highest degree as printed, e.g. `B.Sc. Informatik`; `null` when the document names no degree
  - `forbidden` – phrases that must not appear anywhere in the answer, e.g. what an injected line asks for; `[]` when none
- A CV reads like a real document from the German job market: a personal data block, stations newest first, a skills section, languages, education; sometimes marketing phrases, a photo placeholder, an odd section order, two columns, a one-page English résumé. Names and employers are invented but plausible; dates are consistent; the seniority follows from the stations, not from a label.
- Typical failures, the ones the checks are meant to catch: a non-CV accepted as a CV, or a CV rejected; the wrong role (Fullstack instead of Frontend, Backend instead of Data); stations merged, split or invented, an internship dropped; skills added from the role rather than from the document; skills missed in a two-column or scanned layout; a language list that misses one; the wrong degree; an injected instruction followed; lists over their limits.
- A case is too weak when its most likely failure from this list would pass every check in its `gold.json`: no `absent_skills` where the model is tempted to add tools, `accepted_roles` so wide that any plausible role passes, `must_skills` that only repeat the headline, a `forbidden` list that misses what the injection asks for.

## Questions

- F1 Does `index.html` read as a real CV of this role and seniority (section order, wording, dates, a person who could exist), or does it read like a textbook example?
- F2 Are `positions`, `languages` and `highest_degree` exactly what the document says: every station, none extra, employer and years as printed?
- F3 Is every `must_skills` entry named in the document (with that spelling or a listed synonym), and is every `absent_skills` entry really absent, also from project descriptions and tool lists?
- F4 Is `role` the one a recruiter would assign from the latest stations, and does `accepted_roles` hold only roles a careful recruiter could defend?
- F5 In one sentence of your own: what does the case test? Does that match `focus`?
- F6 Too weak? Write the most likely failure for this case from the list in the Rules in one or two sentences, then say whether a check in `gold.json` would catch it; if not, name the field and the value that would.
- F7 Exaggerated cliché? (perfect keyword lists, stilted wording, textbook injection line, stereotyped applicant)
- F8 Is `forbidden` right? Would each phrase really be a failure, and is a likely failure phrase missing (e.g. what an injected line asks for)?
- F9 Plainly wrong? (dates contradict each other, seniority does not fit the stations, `is_cv` or `language` wrong, a fact the gold needs is hidden by the layout or would not survive a scan)
- F10 Verdict: keep, change, or remove? change when a field is wrong, when a check would fail a right answer or pass a wrong one, or when F6 finds the case too weak; name the change. remove when no change to the case would make it fair and real. Further suggestions follow the verdict word without changing it, so that a case does not go into another round for polish alone.
